## 并行失控

* 该并行的被串行：模型一轮只发一个 tool_call，被拆成两轮检索 + 两次模型调用，延迟直接翻倍。
* 不该并行的被并行：同一轮里 crawl_guba 和 search_posts 一起发出，写库还没落，读库已经返回旧结果，最后答案里「刚入库 300 条」和「库里只有 20 条」同时出现。
* 同一轮两个 crawl_guba 打同一个代码：两套 Scrapy 子进程同时跑，同一批帖子重复入库； 懒加载没加锁，首次并发还会重复编译图。

#### 标签处理


```python
# server/mcp/claw/tools.py 旁边加一张表, 和工具注册一一对应
READ, WRITE = "read", "write"

SPECS = {
    # scope 决定「谁和谁冲突」: 同代码的写会挡同代码的读, 跨代码互不干扰
    "search_posts":  {"mode": READ,  "scope": lambda a: a.get("claw_param") or "*"},
    "get_data_info": {"mode": READ,  "scope": lambda a: a.get("claw_param") or "*"},
    "crawl_guba":    {"mode": WRITE, "scope": lambda a: a.get("claw_param") or "*"},
}
```

* 判定规则：
    * 读 × 读、不同 scope → 并行
    * 读 × 写、同 scope → 互斥，读让写
    * 写 × 写、同 scope → 只跑一次

---
#### 解决方案

**1) 用读写锁按 scope 分片**


```python
# server/core/claw_chat.py
from collections import defaultdict
from contextlib import asynccontextmanager

_cond = asyncio.Condition()
_readers: dict[str, int] = defaultdict(int)
_writers: dict[str, int] = defaultdict(int)

@asynccontextmanager
async def _rw(scope: str, mode: str):
    async with _cond:
        if mode == WRITE:
            while _writers[scope] or _readers[scope]:
                await _cond.wait()
            _writers[scope] += 1
        else:
            while _writers[scope]:      # 有写在跑就先让, 不会被写穿
                await _cond.wait()
            _readers[scope] += 1
    try:
        yield
    finally:
        async with _cond:
            if mode == WRITE:
                _writers[scope] -= 1
            else:
                _readers[scope] -= 1
            _cond.notify_all()


async def _dispatch(name: str, args: dict) -> str:
    """所有工具调用统一走这里, 并行交给 gather, 冲突交给锁"""
    spec = SPECS[name]
    async with _rw(spec["scope"](args), spec["mode"]):
        return await _call_tool(name, args)
```

进程内的锁只对本进程有效。多 worker 部署时得换成 PG advisory lock 或 Redis 锁

**2) 把有依赖的两步合并为一个入口**

只加锁不够：读让写的结果是「读得晚」，不是「读得新」。用户说「拉一下 002526 再总结情绪」，正确顺序是采集落库 → 再检索。与其赌模型会不会分轮，不如把这两步合成一个工具，让它没机会拆。

```python
@tool
async def crawl_then_analyze(claw_param: str, query: str, date: str = "") -> str:
    """先采集指定代码, 入库完成后再按问题检索。两步有依赖, 不要拆开分别调用。

    Args:
        claw_param: 6 位股票代码, 如 002526
        query: 采集完之后要回答的问题
        date: 可选, 8 位日期 YYYYMMDD
    """
    await _dispatch("crawl_guba", {"claw_param": claw_param, "date": date})
    return await _dispatch("search_posts", {"query": query, "claw_param": claw_param})
```

对应地，system_prompt 里原来的第 5 条改成「需要先采集再分析时，只调 crawl_then_analyze，不要同时调 crawl_guba 和 search_posts」。

**3) 同 key 的写做幂等，重复触发只跑一次**

模型重试、用户连点、同一轮里两个调用，都会打同一个代码。别让它变成两次 Scrapy。

```python
_inflight: dict[tuple[str, str], asyncio.Future] = {}
_guard = asyncio.Lock()

async def crawl_once(claw_param: str, date: str | None):
    key = (claw_param, date or "")
    async with _guard:
        fut = _inflight.get(key)
        if fut is None:
            fut = asyncio.ensure_future(_do_crawl(claw_param, date))
            _inflight[key] = fut
            fut.add_done_callback(lambda _: _inflight.pop(key, None))
    return await asyncio.shield(fut)   # 后到的直接复用进行中的那一次
```

#### 该并行的：不下沉到模型，下沉到工具

模型天然保守，一次只发一个调用。你在 prompt 里写「可以并行」，它也只是偶尔并行。可靠的做法是把批量放进工具参数里：一次调用干完 N 件事。

```python
@tool
async def compare_stance(claw_params: list[str]) -> str:
    """一次对比多个股票代码的立场分布, 不要拆成多次调用。

    Args:
        claw_params: 6 位股票代码列表, 如 ["002526", "002777"]
    """
    sem = asyncio.Semaphore(4)   # ONNX 推理吃 CPU, 并行度压住

    async def one(param: str) -> dict:
        async with sem:
            return await asyncio.to_thread(service.stance_overview, param)

    rows = await asyncio.gather(*(one(p) for p in claw_params))
    return "\n".join(
        f"{r['claw_param']}: 共 {r['total']} 条, {r['stance']}" for r in rows)
```

两个细节别踩：

* `stance_overview` 是同步的，必须 `to_thread`，否则一次检索就把 event loop 堵死，其它工具的并行全是假的。
* 线程池默认 32，ONNX 自己还会开线程，不设信号量容易把机器压满，反而比串行慢。本地实测 4 左右比较稳。

prompt 里也补两句，成本最低的收益（配合上面的编排入口，别让并行指令和依赖规则打架）：

```
7. 互不依赖的查询放在同一轮里一起发, 例如同时查两个代码的立场, 不要一个一个问。
8. 有先后关系的不能并行: 先采集再检索, 先采集再看统计。需要先采再查时, 用 crawl_then_analyze。
```

#### SSE 别串台

[claw_chat.py](file:///Users/Zhuanz1/code/PY/agent-plan/server/core/claw_chat.py#L61-L66) 现在推的事件只有 `event` 和 `data`，一旦并行，前端分不清这条 progress 是哪个调用推的。事件体统一加 `call_id`，前端按 id 分组渲染。

进度 sink 现在是进程级 ContextVar，靠 asyncio 给每个 task 复制上下文才勉强隔离。工具里一换线程、或者中途再套一层 task，事件就会串到别的调用上。改成注册表：

```python
# server/mcp/claw/service.py
_sinks: dict[str, Callable[[dict], None]] = {}
_current: ContextVar[str | None] = ContextVar("claw_call_id", default=None)

@contextmanager
def relay_progress(call_id: str, sink: Callable[[dict], None]):
    _sinks[call_id] = sink
    token = _current.set(call_id)
    try:
        yield
    finally:
        _sinks.pop(call_id, None)
        _current.reset(token)

def emit_progress(event: dict) -> None:
    sink = _sinks.get(_current.get() or "")
    if sink is not None:
        sink({**event, "call_id": _current.get()})
```

`crawl_guba` 里 `relay_progress(lambda event: ...)` 改成 `relay_progress(call_id, ...)`，`call_id` 直接取 `runtime.tool_call_id`。

#### 确认逻辑

* 每轮 `len(AIMessage.tool_calls)`：长期恒等于 1，说明并行根本没发生，是 prompt 和工具粒度的问题。
* wall time 拆三段：`model_wall` / `tool_wall` / `queue_wall`。并行生效后 `tool_wall` 要明显小于各工具耗时之和；如果等于，说明锁加多了。
* 同 scope 写冲突次数、`crawl_once` 去重命中次数，这两个数应该 > 0（有流量时），否则闸门没接上。
* LangSmith 里看同一轮的多个 span：时间轴重叠才是真并行，台阶状就是还在串行。
* 三条回归：
  - 「002526 和 002777 谁的消极多」→ 一轮两个 search_posts，不是两轮。
  - 「拉 002526 再看情绪」→ 先落库再检索，sources 里能看到刚入库的新帖。
  - 连点两次同参数采集 → 只跑一次 Scrapy，第二次直接拿第一次的结果。

---
#### 落地顺序

1. 读写锁 + `crawl_once` 幂等（这是正确性问题，先堵数据污染）
2. `crawl_then_analyze` 这类编排入口（把依赖焊死，减少模型自由发挥的空间）
3. 工具内部 `gather` + prompt 并行提示（这一步才是降延迟）
4. `call_id` 打通 SSE、补三段耗时打点（看得见才谈得上调）

不要把顺序反过来。先追延迟容易把「读旧库」的问题放大：并行越多，读到写之前快照的概率越高。
