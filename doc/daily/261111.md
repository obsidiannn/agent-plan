## 失败处理分级

* 现状：一个 `try/except` 套住所有工具，出错就 `for _ in range(3)`。
* 对查询：三次重试只是把失败延迟了三倍，还要多占三个模型轮次，最后大概率还是同样的错。
* 对退款：第一次可能已经扣了，只是响应超时；再重发一次就是第二笔退款。

---
* retry	允许的重发次数	查询 2–3，退款 0–1，外发短信 0
* idempotent	操作本身可重复执行	查询类 true
* idempotency_key	服务端去重用的业务键	退款、下单、支付必填

---
#### 工具自己声明策略

策略跟着工具走，编排层只负责执行，不再统一套模板。退款这类操作即使允许重发，也必须带幂等键，否则服务端无从去重。

```python
from dataclasses import dataclass
from typing import Callable

@dataclass
class ToolPolicy:
    retry: int = 0
    idempotent: bool = False              # 天然可重复执行
    idempotency_key: Callable | None = None
    backoff: float = 0.5

POLICY = {
    "search_order": ToolPolicy(retry=3, idempotent=True),
    "get_user":     ToolPolicy(retry=2, idempotent=True),
    "issue_refund": ToolPolicy(retry=1, idempotency_key=lambda a: a["refund_id"]),
    "send_sms":     ToolPolicy(retry=0),
}
```

幂等键用业务单据号（`refund_id`、`order_id`），不要用随机 UUID。随机键只能保证同一次进程内的重试被去重，进程重启后又是一笔新单。

---
#### 先分类异常，再决定重不重发

* 根据异常类型决定策略, 比如400 类型不再重复

```python
import httpx

def classify(e: Exception) -> str:
    if isinstance(e, (httpx.TimeoutException, httpx.NetworkError)):
        return "ambiguous"                # 不确定对方执行了没有
    if isinstance(e, httpx.HTTPStatusError):
        code = e.response.status_code
        if code == 429:
            return "throttled"
        if 500 <= code < 600:
            return "server"
        if 400 <= code < 500:
            return "client"
    return "fatal"                        # 业务错误、解析错误
```

* ambiguous：超时、连接被重置。对方可能已经成功，必须先查后重发。
* throttled：429，按 `Retry-After` 退避，别按自己的固定间隔硬冲。
* server：5xx，可以重试，但只对确认幂等的操作。
* client / fatal：参数错、鉴权失败、余额不足、单据状态不合法，一律不重试。

#### 执行器按策略分四路

```python
import asyncio, copy

async def call_tool(name: str, args: dict, invoke) -> dict:
    p = POLICY[name]
    args = copy.deepcopy(args)
    if p.idempotency_key:
        args["idempotency_key"] = p.idempotency_key(args)
    resend_safe = p.idempotent or p.idempotency_key is not None

    last, kind = None, "fatal"
    for attempt in range(p.retry + 1):
        try:
            return await invoke(name, args)
        except Exception as e:
            last, kind = e, classify(e)

            # 结果不明又没有幂等键，重发就是赌对方没执行
            if kind == "ambiguous" and not resend_safe:
                break
            if kind in ("client", "fatal"):
                break

            # 有幂等键的非幂等操作：先查上一次到底成没成
            if p.idempotency_key and not p.idempotent:
                got = await invoke(f"{name}_status",
                                   {"idempotency_key": args["idempotency_key"]})
                if got["status"] == "success":
                    return got            # 上一次其实成功了，超时只是响应丢了
                if got["status"] not in ("not_found", "failed"):
                    break                 # 处理中，等结果，别插队

            if attempt < p.retry:
                await asyncio.sleep(p.backoff * 2 ** attempt)

    # 不往上抛，结构化返回给模型
    return {"ok": False, "error": kind, "detail": str(last)}
```

---
#### 重试救不回来的那部分

* 失败结果作为 ToolMessage 回给模型，带上 `error` 类型和原始报错。
* 非幂等操作最终失败，落一条补偿记录（单据号、参数、错误码）
* 重试预算并入 `max_tool_calls`。一个工具重试三次就是三次工具调用 
* 同一工具连续失败超过阈值，短时间直接返回失败，不再发请求，避免故障下游被重试放大。
